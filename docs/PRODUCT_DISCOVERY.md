# 商品設計と需要検証

この文書は、AI Web Site Agentを「安全な生成・レビュー・更新補助」として検証するための作業基準です。YouTube投稿、外部公開、決済、収益化設定はまだ有効化しません。

## 優先する実装

1. 業種別テンプレートで最初の入力を短くする。
2. 無料枠の範囲で、必要な場合だけ引用付きのコンテンツ計画を作る。
3. 生成→レビュー→承認→更新を同じ案件で繰り返せるようにする。
4. 個人情報を保存せず、まず端末内の利用回数・再利用回数を確認する。
5. 再利用と継続利用の需要が確認できてから、有料プランを設計する。

## 外部AIを設計会議へ参加させる方法

GitHub Actionsの [Design council safely](https://github.com/nyu1791-collab/hf-site-agent/actions/workflows/design-council.yml) を手動実行します。main、確認文字列 DESIGN、短い設計課題、必要なら制約を入力し、OpenRouterの無料モデルへ1回だけ読み取り専用のレビューを送ります。

外部AIの役割は次の範囲に限定します。

- 要件の抜け、反対意見、利用者価値、受け入れテストを提案する。
- GitHub、Cloudflare、Hugging Faceへ書き込まない。
- YouTube、決済、有料検索、秘密値を扱わない。
- 回答を司令部が検証し、採用した変更だけを小さなPRにする。

## 需要仮説

最初の検証対象は、次の3つです。

- 小規模事業者: 店舗・サービス案内、FAQ、キャンペーン更新。
- 開発者・ゲームコミュニティ: 攻略、更新履歴、イベント告知。
- 個人制作者: 作品紹介、プロフィール、定期更新。

テンプレートは需要を証明するものではありません。実利用で「同じ利用者が再度更新したか」「レビュー後に承認まで進んだか」を測り、仮説を更新します。

## 指標の扱い

当面は画面の端末内にだけ、生成回数、レビュー回数、更新再利用回数を保存します。これは需要の初期シグナルであり、全ユーザーの集計値ではありません。サーバー側の集計や新しいデータ保存先は、別途承認するまで追加しません。

## 有料化の判定案

次の条件を仮説として観測し、数字が確認できるまで決済を実装しません。

- 初回生成後にレビューまで進む割合。
- 同じ端末で別日に更新を再利用する割合。
- 引用付き計画を再利用する割合。
- 利用者が解決したい業務と、現在の代替手段。

数字は小規模な実利用で確認し、価格・プラン・決済はその後に設計します。
