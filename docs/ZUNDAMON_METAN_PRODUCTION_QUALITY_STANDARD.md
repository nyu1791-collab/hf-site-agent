# ずんだもん・四国めたん 制作・品質・時短 永続標準

この文書は、既存の `config/media_audio_motion_retention_policy.json` と `config/media_character_reaction_cache_policy.json` を置き換えるものではありません。既存標準ですでに固定されている口パク・目パチ・話者フォーカス・表情/ポーズ・二重縁取り字幕・英語字幕表記・リアクション素材キャッシュ等はそのまま維持し、制作準備・編集時短・視聴維持・見た目QAの追加ルールだけを整理したものです。機械可読の正本は `config/zundamon_metan_production_quality_policy.json` です。

## 1. YMM4は「毎回ゼロから」作らない

YMM4を使う場合は、キャラ、VOICEVOX、字幕、証拠画像、SE、BGMのトラック、立ち絵の基本位置、安全領域、話者フォーカス、字幕スタイル、BGM初期音量とダッキング、出力解像度/フレームレートを入れた `.ymmp` ベースプロジェクトから始めます。

ヘッドレス環境では、同じ役割を持つ機械テンプレートを使います。`.ymmp` を実際に作っていないのに「YMM4プロジェクトを生成した」と報告してはいけません。

字幕のフォント・二重縁取り・キャラ色・座布団は一度プリセット化して再利用します。YMM4の「お気に入り」やローカルプリセットは時短手段ですが、恒久的な正本はRepositoryのPolicyです。

## 2. PSDは選択肢であり、毎回の必須ダウンロードではない

権利確認済みのPSD/レイヤー立ち絵はYMM4用に使用できます。ただし登録済みShellと事前生成済みリアクションパックで必要な口・目・眉・腕・表情・記号が揃う場合、PSDを追加取得する必要はありません。

新しいPSDや第三者素材を使う場合も、動画ごとに再取得せず、権利・provenanceを保持したキャッシュへ一度だけ入れます。第三者の原本や派生画像はRepositoryへ直接コミットしません。

## 3. 台本ファースト

タイムラインを組む前に、最低限 `speaker / voice_text / caption_text / emotion / visual_beat / sfx_beat` を持つ構造化台本を作ります。現在の事実を扱う場合は claim/source のIDも紐付けます。

`voice_text` はVOICEVOXが自然に読める文字列、`caption_text` は視聴者に見せる正式表記です。たとえば音声が「オープンエーアイ」でも字幕は `OpenAI` とします。

YMM4が対応する場合は台本を一括投入し、ヘッドレスでは同等の決定論的インポートを使います。AIによる対話台本生成は許可しますが、AIが作った事実主張がそのまま根拠になるわけではありません。

## 4. VOICEVOX辞書を使い回す

固有名詞・専門用語・英語略語の読みを毎回手修正しないよう、`surface_term / voice_reading / caption_spelling / revision` を持つ再利用辞書を使います。

例: `AI → エーアイ → AI`、`OpenAI → オープンエーアイ → OpenAI`、`Anthropic → アンスロピック → Anthropic`、`Hugging Face → ハギングフェイス → Hugging Face`。

読み上げのカタカナを字幕へコピーするのは禁止です。

## 5. 話速・抑揚は1.1〜1.2を「開始値」にする

ショートやニュース解説では、話速と抑揚を1.10〜1.20付近から試すのを標準的な開始点にします。ただし絶対値ではありません。固有名詞が聞き取りにくい、重大ニュースで軽く聞こえる、複雑な説明で理解を阻害する場合は下げます。

最終タイムラインは文字数推定ではなく、生成したWAVの実時間を `ffprobe` で測って決めます。

## 6. BGM・SEはライブラリ優先

よく使うBGM/SEは、権利確認済みのRepository registry/cacheを優先します。YMM4の「お気に入り」は手動編集の高速化に使えますが、権利証拠の代わりにはなりません。

声の最中はダッキングを行い、-18dB付近を開始目安にします。ただし既存音量測定ルールと聴き取りやすさが最優先です。

SEは「画面が変わるたび必ず鳴らす」方式にはしません。証拠提示、重要な数字、強いリアクション、警告、確認、章転換など意味のある視覚イベントに同期させます。毎カットSEはマンネリと過剰演出につながるため禁止です。

## 7. カメラ・シェイク・フィルター

ズーム/パンは盛り上がり、ツッコミ、証拠への注目など意味のある場所で使います。通常の強調は1.08〜1.20倍程度を目安とし、常時ズームは禁止します。

シェイクや一時的な暗転/色変化は強い驚き・ショック・ツッコミで短く使えます。ただし重大事故・死傷・災害などセンシティブな内容ではコミカルな揺れや派手なフィルターを抑えます。

大SE・大ズーム・巨大テロップ・キャラ登場を同時に重ねるのは原則避け、1ビートの主役を一つにします。

## 8. 「2〜3秒ルール」は視覚状態の変化として運用

ショートでは2〜3秒程度を、次の意味ある視覚変化を検討する目安にします。ただし2〜3秒ごとに新画像をダウンロードするという意味ではありません。

表情/ポーズ変更、リアクション記号、証拠写真/図解、クロップ・パン・ズーム、話者フォーカス、字幕の強調、ポインタ/ハイライト、意味のあるカットなどのいずれかで十分です。意味がないのに変化を入れることはしません。長尺説明やセンシティブ場面では、必要なら長めに保持します。

## 9. 冒頭1〜3秒はフック優先

ショート/ニュース解説は、原則として「こんにちは」「今日のニュースです」のような汎用あいさつから始めません。1〜3秒で結論、重要な利害、強い問い、証拠の予告、意外な対比のいずれかを提示します。

ただし安全上必要な注意書きや重大テーマの文脈説明が先に必要な場合は例外です。フックは本編と一致させ、釣り表現にはしません。

## 10. ジェットカットは“事故的な無音”だけを削る

意味のない間、重複したターン間隔、編集上の空白は詰めます。しかし、強調前後の短い静寂、質問の返答待ち、重大テーマの呼吸、意図的なSILENCEは残します。

語尾を切ったり、不自然な畳みかけにして理解を落としたりしてはいけません。「無音を全部消す」は禁止です。

## 11. 手動YMM4作業の時短

手動編集をする場合は、リップル削除、複製、分割/カット、タイムライン移動など頻繁な操作をショートカットへ割り当てることを推奨します。ただしこれは人間の操作速度を上げるための設定で、ヘッドレス動画のmachine QA必須条件ではありません。

## 12. 速度のために品質ゲートを落とさない

高速化はテンプレート、キャッシュ、一括処理、辞書再利用、健全なCheckpoint再利用で行います。権利確認、事実確認、口パク、目パチ、字幕同期、音量、decode、safe-zone、最終machine QAを省略して速く見せることは禁止です。

## 13. 口パクは「動いているか」ではなく「顔に正しく収まっているか」まで見る

今回の制作で、口差分自体は切り替わっていても、合成位置や見た目が不自然なら視聴品質として失敗することが分かりました。したがって「口パクが存在する」だけでは合格にしません。

口差分は元絵と同じフルキャンバス座標を使うか、クロップ素材ならキャラクター別のアンカー情報を必ず持たせます。同時に有効な口レイヤーは1キャラ1つです。ずんだもん・四国めたんのそれぞれで、閉じ口・小開き・開き口を軽量Fixtureに並べ、鼻・目・輪郭への侵入、口の浮き、二重口、透過処理による肌や線画の欠けがないことを本編レンダー前に確認します。

Fixtureは口素材だけを切り出して見るのではなく、実際の顔全体へ合成した状態で確認します。同じ source SHA、reaction-pack revision、出力寸法、スケール、アンカー条件ならFixture結果を再利用します。毎フレーム同じ検査を繰り返す必要はありません。

## 14. 説明パネルは「暗ければ見やすい」と決めつけない

ニュースや技術説明で大きな説明カードを出す場合、黒に近い濃紺を大面積の標準色にしません。中明度のネイビー、青、シアン、ティール、紫などを基本とし、図のノードや矢印はさらに明るい差し色で分離します。背景の暗化も、画面全体が灰色・黒っぽく沈むほど強くしません。

暗色テーマ自体は禁止しません。重大・深刻な話題では暗い処理が適切な場合があります。ただし通常のニュース解説では「文字コントラスト」だけでなく「画面全体の明るさ・軽さ」も見ることを標準にします。機械可読Policyの輝度レンジは開始目安であり、絶対的なカラーグレーディング値ではありません。今後、実際の投稿データで検証されるまでは固定の成功値として扱いません。

## 15. 字幕は文字数より文節・意味の切れ目を優先

既存の1行最大文字数は安全領域の上限です。「上限まで詰めてから機械的に切る」方式ではありません。句読点、節、自然な文節、助詞のまとまり、実際の読み上げフレーズを先に見て、自然な位置で短めに区切ります。

日本語の禁則処理を守り、助詞や助動詞だけを次の行へ置くことをできるだけ避けます。`OpenAI`、`Anthropic`、`Hugging Face`、人名、製品名、略語、技術語、意味的に結びついた数値＋単位は途中で切りません。表示幅を測れる場合は文字数よりピクセル幅を優先します。文字列のコードポイントを一定数ずつ切る実装は禁止です。

## 16. フルレンダーの前に安い見た目QAを通す

90秒の動画を全部書き出してから口元・字幕・配色ミスを見つけるのは遅すぎます。キャラや説明レイヤーを変更した場合は、本編の前に低解像度プレビュー、短いFixture、またはContact Sheetを作ります。

確認対象は固定時刻だけではなく、失敗しやすい場面を選びます。冒頭3秒、ずんだもん／めたんの閉じ口と開き口、目パチ、最も密な字幕、最長の英字トークン、最も暗い説明パネル、最も明るい説明パネル、安全領域端、話者／聞き手フォーカスを含めます。ここで問題があれば高コストな全編レンダーへ進みません。

ただし、変更していない低リスク工程まで毎回同じプレビューを繰り返しません。口元はキャラレイヤー、明るさ・コントラストは説明パネルレイヤー、字幕幅・改行は字幕レイヤーで一次検出し、完成後のサンプル確認は最終的な回帰確認として使います。

フルデコードPASSは技術的に再生できる証明であって、見た目が良い証明ではありません。ユーザーへ渡す前には最終動画からも代表フレームを確認します。

## 17. 修正はレイヤー単位で最小再レンダー

字幕の区切りだけを直すためにVOICEVOXやキャラ素材を作り直しません。説明パネルの色だけなら証拠／説明レイヤーと最終合成だけ、口アンカーだけならキャラレイヤーと最終合成だけを無効化します。音声や台本を変えた場合も、可能なら変更された発話だけを再生成します。

各工程の成果物を内容ハッシュで識別し、依存関係が変わっていない健全な工程は再利用します。「実装が簡単だから全部やり直す」をフルレンダー理由にしてはいけません。フルレンダーが本当に必要な場合は、どの依存関係が変わったのかをジョブログに残します。

## 18. 字幕は4軸で別々に検査する

字幕は、`意味のまとまり / 実際の表示幅 / 音声タイミングと読みやすさ / 強調` を別々の軸として扱います。1つの軸に問題があるからといって、別の軸まで全部作り直しません。

改行は日本語の意味境界が第一です。その後に実フォントの表示幅を測り、画面幅へ入るかを機械的に確認します。文字数は最後の安全ヒューリスティックです。字幕の開始・終了はテキスト長の推定ではなく、測定済みVOICEVOX音声タイミングを使います。

強調色や拡大は意味分割後に適用し、強調のせいで表示幅・安全領域・タイミングが壊れていないか確認します。日本語字幕の「1秒何文字なら必ず成功」といった固定値は、実測データがない限り恒久ルールにしません。

## 19. 動きは多さではなく「1ビートの主役」を管理する

動きを増やせば視聴維持が上がる、と決めつけません。意味のある1ビートにつき、主役となる大きな動きは原則1つにします。証拠カードが主役ならキャラは邪魔をせず、話者フォーカスが主役なら背景側の動きを控えます。

喋り出しバウンスはこれまでどおり小さなアクセントとして使えますが、それ自体を大きな主役モーションとして扱いません。聞き手の目パチ・小さな表情・微動は補助モーションです。常に何かを動かす必要はなく、落ち着いた静止状態もデザインの一部です。

TikTok広告の「刺激を増やす」知見は参考にはしますが、通常のニュース動画へそのまま普遍法則として持ち込みません。重大テーマでは落ち着きと信頼性を優先します。

## 20. 視聴維持は「釣る」のではなく、約束→証拠→納得で作る

YouTubeの公式ガイダンスでは、最初の数秒で見るか離れるかが決まりやすく、タイトルやサムネイルで約束した価値を冒頭で早く届けることが重要です。したがって、ショートやニュース解説では、フック後すぐに「この動画で何が分かるか」を伝えます。ただしフック自体ですでに十分明確なら、同じ内容を重複して読み上げません。

核心の証拠を不自然に30秒以上隠して引っ張るような編集は標準にしません。ずんだもんと四国めたんの対比・質問・訂正は、実際の論点を分かりやすくするために使い、存在しない対立を演出しません。

好奇心の「続きが気になる」は使ってよいですが、その問いは動画内で解決します。終盤は結論・実用的な意味・判断材料を先に渡し、`続きは次回` のような曖昧な締めだけで終わらせません。最後に問いを残す場合も原則1つまでにします。

## 21. 視聴維持の工夫は投稿後データで昇格させる

「この動きなら伸びる」「この字幕密度なら伸びる」「この色なら伸びる」といった創作上の仮説を、数本の感覚だけで恒久ルールへ昇格させません。

可能な場合、YouTube Shortsでは `選んで視聴 / スワイプ離脱 / 平均視聴時間 / 平均視聴率 / retention curve / top moments / dips / spikes` を使います。TikTok等は、そのプラットフォームが実際に提供する指標だけを使い、存在しない数値を補完しません。

比較はできるだけ同じ動画形式・近い長さ同士で行います。単発のバズ動画を基準にしません。テストでは可能な限り主な変数を1つに絞り、見る指標と品質ガードレールを結果を見る前に決めます。

口元、字幕崩れ、暗すぎる説明パネル、事実誤り、権利違反などの品質失敗動画は、視聴維持テストの比較対象として合格扱いにしません。視聴数が伸びても品質ゲートを破った変更は正本へ昇格させません。

## 22. キャッシュは「同じファイル名」ではなく入力Manifest一致で再利用する

再利用する成果物は、Policy版、素材IDとハッシュ、reaction-pack版、口アンカー、字幕ルール、説明パネルProfile、VOICEVOX話者・パラメータ・本文ハッシュ、出力解像度、エンコーダ／Filter版、依存Stageのハッシュまで含む入力Manifestと紐付けます。

Manifestが同じなら再利用し、どれかが変われば影響を受ける成果物と真の依存先だけを再生成します。単純に「前回のStageハッシュがあるから使う」だけでは、古い口アンカーや字幕ルールを再利用する危険があるため禁止します。

この仕組みにより、品質を落とすために工程を飛ばすのではなく、**品質条件が同一であることを証明できた成果物だけを高速に使い回す**ことを標準とします。
